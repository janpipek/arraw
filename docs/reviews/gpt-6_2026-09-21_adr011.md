Review of ADR 011 — 2026-09-21

Reviewed [ADR 011](../adr/011-a-plan-spatial-passes-and-one-pointwise-chain.md), including its latest checkpoint revision (`2d3480c`), against ADRs 007–010, the feature brief, the reimplementation plan, and the current processing code. This is a design review; deliberately deferred implementation is not a defect.

The shared resolved plan, fusion of adjacent pointwise operations, and comparison of stage prefixes are reasonable choices. Three contract gaps should be resolved before implementing the proposed interfaces.

1. **[P2] Distinguish intermediate samples from resumable checkpoints.**

   Location: ADR 011, lines 46–54 and 63–70.

   The first paragraph permits `stopAfter` at intermediate stages, explicitly for the curve-input histogram. The later paragraph says `stopAfter` produces a `RenderCheckpoint`, but only spatial boundaries may be checkpoints. The consequences again promise inspection inside the pointwise chain. A stop immediately before the tone curve therefore has no consistent return contract: either it is forbidden, defeating the first caller, or it creates a checkpoint that the later rule forbids.

   Keep arbitrary named pointwise taps, while restricting which outputs can be resumed. Two workable interfaces are a sampled result with an optional resumable checkpoint, or separate operations for sampling and checkpoint creation. In either case, distinguish pointwise tap identifiers from pass-boundary identifiers; the five blocks in `stagesOf` cannot identify an internal curve-input tap.

   Acceptance example: render a curve-input histogram and a final image from the same pre-pointwise checkpoint. The histogram must stop at the requested internal stage; attempting to resume from that histogram input must have an explicitly defined outcome. Specify the sample encoding too, since ADR 010 places that histogram in perceptual coordinates rather than the usual linear working encoding.

2. **[P2] Include source revision and relevant render context in checkpoint compatibility.**

   Location: ADR 011, lines 25–30, 63–83 and 89–105.

   The checkpoint records which photograph produced it, and compatibility compares prefixes of a plan described as holding what the settings imply. This leaves the relationship to source revisions and request-dependent execution unspecified. Photograph identity and unchanged settings are insufficient: reloading changed source pixels under the same photograph identity must invalidate its checkpoint. Likewise, an early-downsampled preview's noise-reduction result cannot automatically satisfy a full-quality export with identical settings. ADR 007 explicitly permits early preview downsampling, and the reimplementation plan (§9, lines 427–435 and 490–502) already requires revision, resolution and quality information.

   The statement that a plan holds everything stages consume can accommodate these inputs, but the ADR should explicitly require that it does. Otherwise the shown prefix comparison can report equality while the inputs or execution differ. Plan comparison cannot detect a dependency omitted from both plans.

   Either resolve the plan from an immutable source revision, settings **and render request**, placing each execution dependency in its relevant stage block, or validate a separate checkpoint context before comparing plan prefixes. Source identity must include a content generation or equivalent immutable identity. Include actual sampling/region and quality wherever they affect the cached prefix; a downstream-only target-size change should still permit reuse when that prefix is unchanged. If large resource revisions are local counters, pair them with resource identity and retain the corresponding immutable payload.

   Acceptance examples: reject reuse after source replacement; reject an incompatible draft-preview checkpoint for final rendering; retain reuse after an exposure-only change. These establish both correctness and the intended selective invalidation.

3. **[P2] Give the pointwise function explicit per-pixel coordinates.**

   Location: ADR 011, lines 15–18 and 32–38.

   The ADR includes vignette and grain in the fused chain and acknowledges that pointwise operations may depend on coordinates, but defines the chain as `developPixel(plan, colour)`, a pure function of one colour. With the same photograph-level plan, two identical input colours necessarily produce identical outputs. That cannot express a vignette that treats the centre and edge differently, or a spatial grain pattern. ADR 009 (lines 74–79) explicitly assigns both effects composition-frame coordinates. Local mask evaluation will need its corresponding coordinates as well.

   Extend the future contract to something like `developPixel(plan, pixelContext, colour)`, where the context supplies explicitly framed coordinates and the plan supplies shared transforms and any deterministic grain seed. Alternatively, pass a sample value containing colour and position. Both preserve purity and fusion while giving the CPU and shader the same inputs. This does not require adding unused parameters to today's matrix-only implementation.

   Acceptance example: equal-colour pixels at the centre and edge differ with vignette enabled, while evaluating the same pixel twice under the same plan is deterministic. Compare CPU and GPU at matching coordinates, including after crop and rotation.

Validation: repository and contract inspection, with counterexamples traced through the proposed interfaces. No tests were run: the disputed tap/checkpoint contracts are not implemented, and the current plan tests exercise only white balance, the matrix and exposure. Only this review document was added; production code and ADRs were left unchanged.
