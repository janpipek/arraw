# Review of ADRs 007–009

Reviewed on 2026-09-21 against the current working tree. This is a design review of the proposed contracts, checked against ADRs 001/003/005, the feature brief, the reimplementation plan, and current import/build code. The absence of the proposed implementation is intentional and is not a finding.

Three actionable findings follow. The camera-space boundary, plain settings, and typed coordinate frames are reasonable directions, but the white-balance contract needs correction before implementation.

1. **[P1] Preserve the calibration needed to convert Kelvin into camera gains.**

   Locations: [ADR 007, lines 40–42 and 53–61](../adr/007-camera-primaries-travel-with-the-pixels.md#decision), [ADR 008, lines 74–88](../adr/008-develop-settings-and-their-descriptors.md#decision).

   `rgb_cam` is sufficient to reproduce LibRaw's final matrix operation on its already-scaled camera pixels. It is insufficient, with `cam_mul` alone, to recover the illuminant or derive absolute temperature gains. LibRaw's `cam_xyz_coeff` normalises the camera-response rows before inversion and stores their scale separately in daylight `pre_mul`. That information is absent from the proposed `CameraNative`. This is visible in the [LibRaw 0.22.2 implementation](https://github.com/LibRaw/LibRaw/blob/0.22.2/src/utils/utils_dcraw.cpp#L266-L295).

   Reproduced against the installed LibRaw 0.22.2 using two temporary DNGs generated from the repository's fixture writer. The second doubles the first row of `ColorMatrix1`; both retain `AsShotNeutral = (0.5, 1, 0.8)`:

   | Metadata after `open_file` | First DNG | Second DNG |
   |---|---|---|
   | `cam_mul` | `(2, 1, 1.25)` | `(2, 1, 1.25)` |
   | `rgb_cam` | Same matrix | Same matrix |
   | Daylight `pre_mul` | `(0.9999977, 0.9999238, 1.0001656)` | `(0.4999989, 0.9999238, 1.0001656)` |

   The proposed stored values cannot distinguish these calibrations. Consequently, a Kelvin conversion using only those values must give the same answer for both, although their unbalanced camera responses differ. This undermines both as-shot Kelvin recovery and copying absolute temperature across bodies.

   Preserve daylight calibration before processing, or retain a suitable unnormalised camera/XYZ transform with its calibration convention. Also distinguish recorded WB from the gains actually applied during decode, including the missing-WB fallback. LibRaw's `scale_colors` changes `pre_mul` and normalises the applied gains, so reading it only after processing loses its original meaning. See [the scaling implementation](https://github.com/LibRaw/LibRaw/blob/0.22.2/src/postprocessing/postprocessing_utils_dcrdefs.cpp#L103-L203). Define whether `asShotNeutral` means neutral channel values or reciprocal correction multipliers; the current name and comment suggest opposite conventions.

   Validation should cover non-unity daylight calibration, non-unity as-shot WB, missing WB, and temperature/tint → gains → temperature/tint round trips. An identity-matrix fixture alone cannot establish this contract.

2. **[P2] Represent as-shot explicitly instead of defaulting absolute temperature to 0 K.**

   Locations: [ADR 008, lines 25–28 and 94–100](../adr/008-develop-settings-and-their-descriptors.md#decision), [ADR 007, lines 160–162](../adr/007-camera-primaries-travel-with-the-pixels.md#consequences).

   ADR 007 promises that `develop(buffer, {})` applies only the matrix to a RAW. ADR 008 defaults `temperature` to zero, defines it as absolute Kelvin, and requires the renderer to clamp out-of-range values. Applying those rules would resolve the default to the minimum temperature, changing the image's as-shot WB. No rule distinguishes an unspecified/as-shot value from an invalid explicit temperature. A universal nonzero default would also fail for photographs taken under different illuminants.

   Choose an explicit as-shot/custom mode or optional override that is resolved before range validation. Alternatively, require a source-aware settings factory and replace the `{}` rendering promise. State how reset, a sidecar without WB, and a partial preset resolve this state. Verify that an exposure-only edit leaves the decoded as-shot WB unchanged.

3. **[P2] Make the upscale policy expressible through the shared render API.**

   Locations: [ADR 007, lines 93–96 and 123–126](../adr/007-camera-primaries-travel-with-the-pixels.md#decision).

   `RenderRequest` contains only a bounding size, but the CLI promises two distinct outcomes for a 1600-pixel image requested at 2048: keep 1600 normally, produce 2048 with `--allow-upscale`. Those calls cannot be distinguished by the declared request. Always clamping prevents the flag from working; always upscaling violates the default unless every caller computes and clamps the post-crop dimensions itself.

   Add an upscale policy to the request. Alternatively, define `targetSize` as an already-resolved size and provide one shared size-resolution function that handles crop, aspect, and upscale policy. Keep this calculation in the library so the CLI and GUI do not reconstruct geometry independently. Test both policies on the same cropped source.

Two decisions remain unclear in ADR 009; these are questions rather than asserted implementation defects:

- **What shape does a parametric mask preserve through a nonlinear warp?** Lines 37–49 and 104–107 specify sensor storage and inverse transformation of handles. Transforming a linear mask's endpoints does not inverse-transform its entire weight field; a straight line generally becomes a curve under lens distortion. Likewise, an ellipse or circular spot generally cannot retain its exact footprint through a nonlinear warp using only transformed centre/radius values. One coherent policy is to define these shapes in sensor space and display their warped outlines. Another is to preserve the shape drawn in the corrected view using a captured transform or a rasterised sensor-space mask. Choose explicitly, including what changes when a lens profile changes. Also define a metric for scalar radii: normalised x/y positions alone do not say whether a radius is a fraction of width, height, or another reference length on a non-square image.

- **Does a quarter-turn preserve the existing crop's subject?** Lines 59–62 store the crop in the upright frame, whereas lines 99–103 say a quarter-turn changes only the transform. An unchanged off-centre upright crop selects different sensor content after rotation. Either remap the crop on quarter-turns/flips, or define a crop representation whose reference orientation remains stable. If selecting different content is intended, say so. The claim that stored mask geometry needs no rewrite can remain true regardless of the crop policy. Pin the chosen behavior with an off-centre crop and four successive quarter-turns.

No production code, ADRs, or committed fixtures were changed. The pre-existing modification to `AGENTS.md` was left untouched.
